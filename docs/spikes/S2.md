## Run it — cloud part

1. After the coder's branch `claude/foundation-core` is pushed, create a throwaway branch from it named `spike/s2-capture`. In it, copy `hooks-config/spike-s2-capture.settings.json` to `.claude/settings.json` and push. (On GitHub: open the file, copy the content, "Add file" → `.claude/settings.json` on the new branch.)
2. At claude.ai/code, start a **new** cloud session on `<owner>/agent-office`, branch `spike/s2-capture`, permission mode Manual (default).
3. Send this prompt:
   > Use the **architect** subagent to read `README.md` and grep `docs/` for "DECISION REQUIRED". Then use the **tester** subagent to run `node --version` and then `node -e "process.exit(3)"` with Bash (the second one fails on purpose). Then fetch https://code.claude.com/docs/en/hooks.md with WebFetch and reply "done".
4. When it says done, send:
   > Run `npm ci && npm run build -w @agent-office/core && node scripts/spike-s2-export.mjs .spike/s2/linux fixtures/hooks/cloud`. Show me `ls fixtures/hooks/cloud`, then print the `capture` block (not `stdinRaw`) of one PreToolUse capture made inside the architect subagent and one SessionStart capture. Do not commit anything yet.
5. Read the printed output. If no secrets or private text appear in `fixtures/hooks/cloud/`, tell that session: "commit fixtures/hooks/cloud only and push". Copy the two `capture` blocks into this doc's Results section (or paste them to the coder).

`PermissionRequest` and `Notification` may not fire in a cloud session. Record "not observed" for them; the PC run covers them.

## Run it — PC part (Windows)

Prereq: Node 22.13+ and Git on the PC; the repo cloned at `C:\path\to\agent-office`.

1. In PowerShell:
   ```powershell
   cd C:\path\to\agent-office
   git fetch origin
   git checkout spike/s2-capture
   npm ci
   ```
2. **Desktop app:** open a new session in `C:\path\to\agent-office`, send the same prompt as cloud step 3, and approve the Bash command when asked (this should produce `PermissionRequest` and, if you wait about 6 s before approving, `Notification`). Then close the session (`SessionEnd`).
3. **CLI:** in PowerShell, in the same folder, run `claude`, send the same prompt, approve, then type `/exit`.
4. Export and check:
   ```powershell
   npm run build -w @agent-office/core
   node scripts/spike-s2-export.mjs .spike\s2\win32 fixtures\hooks\pc
   git status
   ```
5. Open a few files in `fixtures\hooks\pc\` and check for anything private. If clean: `git add fixtures/hooks/pc`, commit, push to `spike/s2-capture`.
6. Q4: in `.spike\s2\win32\`, look at the SessionStart and UserPromptSubmit captures. If both a `"form": "exec"` and a `"form": "shell"` capture exist, `$CLAUDE_PROJECT_DIR` worked in both forms. If only `exec` exists, shell form failed on Windows (likely PowerShell without Git Bash) and C-07 must use exec form.
7. Q5: note the `bootMs` values of a few Windows captures (and whether Git Bash is installed).
8. Delete `.spike\` when done: `Remove-Item -Recurse -Force .spike`.

Afterwards the coder cherry-picks only `fixtures/hooks/{cloud,pc}/` into the main line, adds expectations to the contract test, and fills in Results. The `spike/s2-capture` branch (with its `.claude/settings.json`) is never merged.

## Q5 measurement note

`bootMs` is the time from the Node process start to the first line of the capture script. It does not include the time Claude Code takes to start the shell (shell form) or the process itself, so the real spawn cost is higher. It is still a fair comparison between exec and shell form and between machines.

**Findings that change the code (for the fixture-refresh task, then C-07):**

1. **Hand-backs arrive as `UserPromptSubmit`.** When a subagent finishes, Claude Code injects its report as a prompt that starts with `<agent-message from="<agent_id>">`. The normalizer must classify these as hand-backs and never show them as the PO's prompt. (Each UserPromptSubmit file appears twice only because the capture hooks run both exec and shell forms.)
2. **`SubagentHandback` and `ToolSearch` are tools.** `SubagentHandback` (Pre/PostToolUse, inside a subagent) carries the report text in `tool_input.message`. Do not show it as a tool line; render it as "reporting back" and scrub the text. `ToolSearch` runs in the main session.
3. **`Stop` is not "team idle".** It fires when the main turn ends even while a subagent still runs, and it carries `background_tasks[]` (`id`, `type`, `status`, `description`, `agent_type`), `last_assistant_message` and `session_crons`. The avatar reducer must keep desks "working" while `background_tasks` lists a running subagent.
4. **Empty-type `SubagentStop`.** Two `SubagentStop` events had `agent_type: ""` with agent ids that never had a typed `SubagentStart`. This confirms the rule: ignore events with an empty `agent_type`.
5. Other observed fields: `prompt_id` (turn id), `permission_mode`, `effort.level`, `model` (SessionStart), `scratchpad_dir`, `duration_ms` and `tool_response` on PostToolUse (Bash: `stdout`, `stderr`, `interrupted`, `isImage`, `noOutputExpected`), `agent_transcript_path` on SubagentStop.
6. `session_id` is a UUID, which passes the `sessionId` charset rule. Cloud ids (`cse_` / `session_`) are still to be checked.
7. An untyped Agent call (no `subagent_type`) was not observed; the `general-purpose` matching rule is still unconfirmed.

### PC, Claude Code CLI, `--permission-mode default` (2026-10-21) — DONE

13 observed captures (branch `spike/s2-capture`, `fixtures/hooks/pc2/`). This fills the gap from the first run.

- **`PermissionRequest` observed.** Payload: `tool_name`, `tool_input`, `permission_suggestions[]` (`addRules` objects). **It has no `tool_use_id`**, no `agent_id`, and no `tool_use_id` to link it to the Pre/PostToolUse of the same call. This confirms the A1.1 choice: bridge-side suppression by `runId`, not linking by `tool_use_id`. It fires after the `PreToolUse` of that call.
- **`Notification` observed.** Payload: `message: "Claude needs your permission"`, `notification_type: "permission_prompt"`. No tool name or id. It fired after the wait, before the decision.
- **`PostToolUseFailure` observed.** Payload: `tool_name`, `tool_input`, `tool_use_id`, `error: "Exit code 3"`, `is_interrupt: false`, `duration_ms`. A Bash command that exits non-zero as its own command produces this, **not** a `PostToolUse`. (Last time the failing command was chained, so the call exited 0.)
- In default mode a harmless command (`node --version`) ran with **no** `PermissionRequest`. Only the command that needed approval fired one. So a missing `PermissionRequest` does not mean a tool was blocked.
- The empty-`agent_type` `SubagentStop` showed up again in this session (no matching typed start). It looks like an internal helper agent that appears in every session. Keep ignoring empty types.
- Event order seen: `PreToolUse` → `PermissionRequest` → `Notification` → (approved) → `PostToolUseFailure`.

### PC, Claude Desktop app (2026-10-21) — DONE

26 observed captures (branch `spike/s2-capture`, `fixtures/hooks/pc-desktop/`), ask-permission mode.

- **Same payload shapes as the CLI** for the shared events. `PermissionRequest` has exactly the same keys as the CLI one. Project hooks fire in the Desktop app, in both exec and shell forms (`bootMs` 27 to 105).
- **One Desktop "new session" produced two sessions in the same folder.** Besides the PO's session, a second "side session" started: its `SessionStart` has no `model`, its first prompt begins `Background (from the session that started this one):`, it only globbed a `side-session-notes` folder under `%APPDATA%\Claude`, then stopped, and it **never sent `SessionEnd`**. The lobby must not show it as a real team session (see rule below).
- **A second injected prompt kind.** Besides `<agent-message from="...">` (CLI run), `UserPromptSubmit` also fires for `<task-notification>...` (a background task finished). Both are system messages, not the PO typing.
- `Notification` came about 6 s after `PermissionRequest`, while other events (a subagent's `Read`, its `SubagentStop`) kept flowing. It is not adjacent to the request.
- The empty-`agent_type` `SubagentStop` appeared here too (once per session).

**Rules for the normalizer and lobby (fixture-refresh task):**
1. A `UserPromptSubmit` is a **system prompt** (not the PO's) when it starts with `<agent-message`, `<task-notification` or `Background (from the session that started this one)`. Never show system prompts as "PO said".
2. A session whose first prompt is a "Background (from the session that started this one)" prompt is a **side session**: hide it from the lobby by default (or label it "side session"). It has no `SessionEnd`, so the 120 s quiet rule is what idles it.

**Cloud findings (no code change needed; contract tests pin them):**

1. **`CLAUDE_EFFORT` is missing** in the hook env for SessionStart, SessionEnd, SubagentStart and UserPromptSubmit (set for tool and stop events). The payload `effort: {level}` field is missing on exactly the same events. Emit and normalize read neither, so nothing changes (tested both ways).

6. `Stop` and `SubagentStop` carry `background_tasks: []` and `session_crons: []` as on the PC.
