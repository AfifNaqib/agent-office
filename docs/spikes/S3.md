## What the script does

`scripts/spike-s3.mjs` has two modes:

- `node scripts/spike-s3.mjs` — **step 1 only.** Finds `claude` on PATH (`where.exe claude`) and runs `claude --version` on each hit with `shell:false`. For a `.cmd` shim it also looks for the `cli.js` the shim wraps and tests running that with `node`. No model usage.
- `node scripts/spike-s3.mjs --run` — step 1, then six short headless runs:

| Step | Run | What it checks |
|---|---|---|
| message | prompt 1 ("count to 40"), then prompt 2 ("reply TWO") sent straight away, while turn 1 runs | Q2, Q5, Q7 |
| stop: interrupt | long prompt (a 600-word story); at the first streamed output it sends `{"type":"control_request","request":{"subtype":"interrupt"}}` on stdin, waits up to 10 s for a `result`, then checks the process still takes a new message ("reply AFTER") | Q3 |
| stop: close-stdin | same prompt; at the first output it closes stdin and times the exit | Q3 |
| stop: kill | same prompt; at the first output it runs `taskkill /PID <pid> /T /F` | Q3 |
| resume ×2 | `--resume <session id>` of the interrupted run and of the killed run, asking "what were you writing?" | Q4 |

Every run uses `claude -p --input-format stream-json --output-format stream-json --verbose --permission-mode default --settings .spike\s3\settings.json`, and the stop runs add `--include-partial-messages`. The settings file adds hooks to these runs only, nothing else: async command hooks that log the event name, plus http hooks to a local server on `127.0.0.1` (random port) that send the header `X-Agent-Office-Run: $AGENT_OFFICE_RUN_ID` (`allowedEnvVars`), which answers Q6.

**Safety rules the script keeps:**

- It runs only the unmodified `claude` CLI, with no Agent SDK and no `--bare`, and it never reads credential files.
- It removes `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` from the child environment, so the runs use your Claude login.
- It spawns with `shell:false` and sends prompts on stdin, never in argv.
- It uses `--permission-mode default`, and every prompt says "Do not use any tools". It never uses `bypassPermissions`.
- The report records whether env vars are **present**, never their values. It also records hook event names (never hook bodies), reply excerpts of at most 120 characters, and the first 300 characters of stderr.
- The report is printed and also saved to `.spike\s3\report.json`. `.spike\` is gitignored.

**Usage:** about six small headless turns on your Claude plan. Watching never uses model usage; this spike does, once.

## How the coder reads the report

- **Q1:**
  - A candidate with `ext: ".exe"` and `ok: true` → `config.claudePath` = that path.
  - Only `.cmd` with `ok: false` (`EINVAL` is expected: Node refuses `.cmd` without a shell) but `wrapsProbe.ok: true` → spawn `node <cli.js>`. Never use `shell:true` (plan §11).
- **Q2:** `secondResultArrived: true` and `secondSaysTwo: true` → FR-023 "write to stdin if alive" works.
- **Q3:** the clean stop needs all of these:
  - `stopInterrupt.resultSubtype` is set within 10 s of the stop;
  - `aliveAfterResult: true` and `acceptsNextMessage: true`.

  If that holds, FR-022 uses the interrupt message and keeps the process. Otherwise, compare `exit.atMs - stopAtMs` for close-stdin against kill:
  - close-stdin may simply let the turn finish, which is not a stop;
  - kill is the plan's fallback.
- **Q4:** `gotResult: true` after both stops → resume is offered after any stop. `sameSessionId` says whether `--resume` keeps the id or forks a new one.
- **Q5:** `hasSessionId: true` on `system/init`.
- **Q6:**
  - `httpHooks` entries whose `runHeader` starts with `runIdPrefix` → the V2-03 permission hook design holds.
  - Empty `httpHooks` but non-empty `commandHooks` → http hooks did not fire, or did not expand the header. That needs an ARCHITECTURE CONCERN before V2-03.
- **Q7:** `parentEnvHas` both `false` (or stripped) and `apiKeySource` not an API key → the subscription was used.

## Assumptions this spike also tests

These come from the plan and the CLI docs, but have not been seen working yet:

- `--settings <file>` adds hooks for one run.
- The interrupt control message shape (`control_request` / `subtype: "interrupt"`) is accepted by `-p --input-format stream-json`. The headless docs do not describe it; that is why S3 exists.
- `--include-partial-messages` streams events before the reply is complete. Without it, the stop tests would fire only after the full reply.
- http hooks expand `$AGENT_OFFICE_RUN_ID` in headers when it is listed in `allowedEnvVars`.

If any of these fails, the report will show it: a non-zero `exit.code`, a `stderrHead` error, or empty hook lists. The coder then adjusts the script or raises an ARCHITECTURE CONCERN. The coder does not change the design silently.

## Results

**Run by the PO on Windows, 2026-10-21, `claude` 2.1.306, Node 22.19.** Subscription login (`apiKeySource: "none"`; both API-key env vars were absent). All answers below are observed, from the PO's report.

| # | Answer | Evidence |
|---|---|---|
| Q1 | **PASS.** `claude.exe` (native install, `%USERPROFILE%\.local\bin\claude.exe`) spawns with `shell:false`. No `.cmd` shim involved. It was not on the default PATH here (PATH is locked on the PO's PC), so `config.claudePath` is needed. | `resolve.chosen`, no `spawnError` in any run |
| Q2 | **PASS, queued.** A second stdin message sent while turn 1 ran was accepted and answered ("TWO") after turn 1 finished (result 1 at 11.8 s, result 2 at 13.8 s). It is queued, not injected mid-turn. | `secondResultArrived`, `secondSaysTwo` |

| Q4 | **PASS.** `--resume <id>` works after the interrupt and after the kill, with the same session id. After the interrupt, the model remembered the story. After the kill, nothing had been saved ("Story never got written"). | `resumeAfterInterrupt`, `resumeAfterKill` |

### Findings that change the design

1. **An interrupted turn fires no `Stop` hook.** In the interrupt run there were 2 `UserPromptSubmit` hooks but only 1 `Stop` (for the second turn). A killed run fires none. **So the bridge must settle a run from the stream-json `result` message (`error_during_execution`) or from process exit, never from the `Stop` hook alone.** This matters for FR-022, V2-02, the avatar "waiting"/"working" state and the permission-card settling rules (A1.1 `run.status`).
2. **Stop = interrupt first.** FR-022: send the interrupt message, wait up to 10 s for `result`; if none arrives, kill the process tree (`taskkill /T /F`) and set status `stopped`. Keep the process alive after a clean interrupt so a follow-up message works.
3. **Message = queue.** The UI should say a message sent during a turn is queued until the turn ends.
4. **Process start costs about 3.5 to 4.5 s** before `system/init` on this PC. Show a "starting" state in the UI.
5. **Resume** is always offered, after interrupt and after kill.
6. `claude` was not on PATH: the bridge config needs an explicit `claudePath` (default `%USERPROFILE%\.local\bin\claude.exe`).
7. Not tested: `.cmd` shims (the PO has the native `.exe`), `cli.js` fallback, permission prompts inside a bridge run (S3 prompts forbade tools).
